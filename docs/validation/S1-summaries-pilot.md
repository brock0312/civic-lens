## 2. 流程與資料

1. **抓速記錄**（`fetch_transcripts.py`）：依「總質詢」「業務質詢」兩個性質翻清單頁，每頁接著打該頁的 `gaz_viewer`（dataIndex 綁 session），取得 viewer id，再取得 PDF。用 gaz_viewer 頁面上的標題核對清單標題，防止 dataIndex 位移。PDF 要以 `%PDF` 開頭。標題含「書面答覆」的跳過（那是市府書面答覆，不是速記錄）。清單上的摘要文字是從起始頁整頁擷取的，常混到上一組，所以**日期與組員一律從 PDF 內文解析**。
2. **切分**（`segment.py`）：規則見 §3。每位議員輸出：
   - `seg_<person_id>.txt`：給 NotebookLM 的來源。每組有標題（組別、日期）與速記錄 viewer 網址；每段發言是一行「〔公報第N頁〕發言人：內容」。
   - `seg_<person_id>.json`：索引。`groups` 記錄每組的組別、日期、組員與組員來源、速記錄網址、PDF 頁序與公報頁碼、本人發言段數與字數、官員答復段數，以及對應的影片深連結。`spans` 記錄每段發言在文字檔中的起訖位置、發言人與頁碼，用來把引文對回頁碼。
3. **NotebookLM**（`summarize.py`）：一個會期一個 notebook，每位議員的文字檔是一個來源（以檔案上傳，檔名當作來源標題）。每次提問都帶 `-s <source_id>`，並用 `-c <新 UUID>` 開新對話。**原因**：CLI 沒有 `--new`，預設會接續上一輪對話（本地快取或伺服器上最近一次），不開新對話就可能把上一位議員的回答帶進來。提示詞的全文在程式裡，要求 3–6 個議題，固定輸出「### 議題：／- 議員：／- 市府回應：」格式；官員只寫職稱、不寫姓名；禁用評價動詞；不寫來源沒有的數字；每句都要附引文。
4. **檢查與審閱稿**（`check_report.py`）：把回答解析成 `{person_id, name, session, issues:[{topic, councilor_points, response, citations:[{source_url, page, cited_text, …}]}], sources, generator, generated_at, disclaimer}`。`source_url` 是速記錄 viewer 網址加 `#page=<PDF 頁序>`，`page` 是公報頁碼。`sources` 每組附速記錄頁碼連結與影片深連結。四項自動檢查（§5）不通過時寫進 `check.problems`，摘要照樣保留。

**深連結實測**：速記錄 `viewer.html?id=…#page=11`，pdf.js 開啟後停在第 11 頁（共 13 頁），已確認可用（2026-09-30 用 headless Chrome 實測一次；之後不再開瀏覽器）。影片連結沿用 V3／M5：分段名稱是「第N組」時用 `Index?id=…&num=N`，否則連到場次頁並註明起始分鐘。

## 3. 切分規則與可靠度

### 3.1 規則（寧可少收，不收錯）

1. **只看本組範圍**：從 PDF 內「XX部門質詢第 N 組」或「市政總質詢第 N 組」的標題開始，到下一個組標題為止。同一份 PDF 的首尾頁常夾著相鄰組的內容。
2. **發言標籤**：行首、以冒號結尾、不含標點，而且以「議員」或職稱結尾的一行（例如「李議員明賢：」「社會局姚局長淑文：」）。也接受半形冒號、重複冒號、「…答覆：」，以及 Word 註解殘留（「王議員閔生：  註解 [呂懿恬1]: ：」）。pdftotext 有時把標籤併到上一行的行尾（「…是否屬於重大陳處長英豪：」）；行尾如果是本份其他地方出現過的標籤，就拆開。
3. **組員**：以公報表頭的「質詢議員」為準，先用全屆議員名單校正：姓名黏在一起（22 份）、頓號分隔、一字之差的錯字（「鐘小平」改成鍾小平），共校正 23 份。表頭組員如果全都沒有發言，就改用影片分段裡組員重疊最多的那一組。第 5 次定期大會沒有觸發；第 6 次定期大會市政總質詢第 9 組有觸發（表頭整段貼成第 1 組的名單）。
4. **歸屬**：組員議員發言，歸該議員。主席發言不收，也不改變目前歸屬（主席插話後官員接著答，仍算原議員的質詢）。官員發言歸目前的議員。非組員的「X議員Y」通常是錯字或插話，遇到時暫停歸屬，接下來的官員答復都不收，直到組員再次發言。因此同組議員交錯發言時，每位議員只拿到自己的發言，以及緊接在後的官員答復。
5. **影片對應**：用組員重疊數加上同一天來比對，**不用組別編號**。第 5 次定期大會交通部門第 8、9 組在公報與影片的編號互換；總質詢跨兩天時影片切成兩段。公報日期有錯字時（財政建設部門第 8、9 組寫成 113 年），退回只比組員。

## 4. NotebookLM 的限制

| 項目 | 狀態 |
|---|---|
| 登入 | ❌ `auth check` 只檢查本地 cookie，回 ok；`auth check --test` 的 token fetch 失敗、`auth refresh` 失敗。**本地檢查 ok 不代表能用**，量產前要用 `--test` 確認。`login` 要在瀏覽器互動，代理程式無法代為完成 |
| 來源數 | 依官方方案：Standard 每個 notebook 50 個來源、Plus 100、Pro 300。全屆每會期 53 人，Standard 要拆成 2 個 notebook（**未實測**） |
| 來源大小 | 試做最大的來源 66,308 字，遠低於單一來源 50 萬字的上限（官方說明，**未實測**） |
| 速率 | 技能文件：遇到 "No result found for RPC ID" 等 5–10 分鐘再試。程式每次提問間隔 20 秒，遇到限制等 600 秒重試一次。每日提問上限依方案而定（**未實測**） |
| 耗時 | **未實測**（技能文件：來源處理 30 秒～10 分鐘） |
| 對話隔離 | CLI 沒有 `--new`，用 `-c <新 UUID>` 開新對話（讀過 `notebooklm/_chat.py`：帶入未知的 conversation id 時歷史是空的） |

## 5. 自動檢查（`check_report.py`，已用自我檢查與假回答驗證）

1. **引文定位**：`cited_text` 去掉空白後，必須是該議員切分文字的子字串（以「…」省略的，各段要依序出現），而且 `source_id` 必須是該議員的來源。定位成功就換算成公報頁碼、PDF 頁序與發言人；失敗就標「引文無法定位」。
2. **禁用詞**：痛批、砲轟、怒嗆、狠批、打臉、嗆、轟、酸。單字詞（嗆、轟、酸）可能誤報（例如「酸雨」），會附上下文給人判斷。
3. **每個議題至少 1 條引文**。
4. **人名**：比對其他 52 位議員的姓名，以及全會期官員發言標籤推出的「姓名」與「姓＋職稱」（例如謝銘鴻、謝局長）。凡是不在該議員自己段落裡的，就標出來。**限制**：中央官員、民眾、媒體這類人名不在名單裡，抓不到，要靠人工審閱（提示詞已要求官員只寫職稱）。

## 8. 風險

1. **公報錯誤多**：表頭、日期、發言標籤都有錯字。程式已處理已知類型，新類型會出現在 audit 的 `others`／`unlabeled`；量產時每個會期都要先看過 audit。
2. **少收**：錯字標籤會讓官員答復被省略，或併進前一段發言，所以摘要可能漏掉部分答復。
3. **NotebookLM 登入會過期**，而且本地檢查偵測不到，量產排程要先跑 `--test`。
4. **非官方 API**：notebooklm-py 是逆向工程的 RPC，Google 改版就可能失效。
5. **摘要品質未驗證**：還沒有實際回答，議題粒度、中性用語、引文定位率都要等第一輪結果出來才知道。
6. **沒有發言的議員**（每會期約 3 人）要另外顯示，不能顯示空白摘要。

## 9. 未解問題

1. NotebookLM 的實際耗時、速率上限、引文定位率（要等登入後才能測）。
2. 第 6 次定期大會交通部門第 1–4 組對不到影片分段的原因。
3. 錯字標籤（例如「萬安：」）要不要建立別名表來修正，還是接受少收。
4. 聲明文字已確認；它在網站上的位置與樣式，等前端設計時再決定。
